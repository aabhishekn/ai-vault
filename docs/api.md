# API and operations reference

Run commands from `backend/` with the virtual environment active. See the root README for setup.

## Database migrations

From `backend/`, with the virtual environment active:

```bash
python -m alembic upgrade head
python -m alembic current
python -m alembic check
```

`app/db/models.py` describes the desired table structure. `migrations/versions/` records the versioned changes used to build that structure. Alembic reads the same database configuration as the application; credentials stay in `.env`. After editing models, generate a migration with `python -m alembic revision --autogenerate -m "Describe the change"`, review it, and apply it with `upgrade head`.

The first migration creates `documents`: UUID ID, filename, unique storage path, content type, positive byte size, processing status, optional summary/error, and a timezone-aware creation timestamp. Valid statuses are `queued`, `processing`, `extracted`, `embedded`, `ready`, and `failed`. Original file bytes will live in local file storage. UUIDs are generated by the Python model on insert.

A migration contains `upgrade()` to apply changes and `downgrade()` to reverse them. The first migration's downgrade drops the table and its data; do not run it against data you want to keep.

## Upload a PDF

Open http://localhost:8000/docs, expand `POST /documents`, click **Try it out**, and choose a PDF. Or from the repository root:

```bash
curl -F "file=@/absolute/path/to/document.pdf" http://localhost:8000/documents
```

Uploads return HTTP 201 with a document ID, original filename, type, byte size, status, and creation timestamp. Files are stored under `storage/documents/` using generated UUID filenames; file paths are not exposed in the response. Metadata is stored in PostgreSQL.

This version accepts `.pdf`, `.png`, `.jpg` and `.jpeg` files whose first bytes match their type (`%PDF-`, the PNG signature, the JPEG signature), limited to 10 MiB. This is a basic signature check, not full parsing; the processing worker validates readability later. The stored file keeps its extension and the document's `content_type` is `application/pdf`, `image/png` or `image/jpeg`. Empty files return 400, unsupported types/headers return 415, and oversized files return 413. Files are removed if saving their database record fails. A process crash between saving the file and committing metadata can still leave an orphan file; reconciliation can be added later.

`queued` means awaiting background extraction. A successful upload automatically queues an RQ job after the file and metadata are saved. Start `python -m app.worker` from `backend/` (with `.venv` active) to process jobs. The embedding stage runs automatically when `OPENAI_API_KEY` is set; set `ENABLE_EMBEDDINGS=false` to disable it.

Run upload validation and failure-cleanup tests from `backend/`:

```bash
python -m unittest discover -s tests -v
```

## Retrieve a document

Use the ID returned by upload to fetch its metadata:

```bash
curl http://localhost:8000/documents/YOUR_DOCUMENT_UUID
```

`GET /documents/{document_id}` returns HTTP 200 with the same metadata fields as upload. An unknown UUID returns 404; an invalid UUID returns FastAPI's 422 validation response. Database errors return a generic 503. This endpoint retrieves metadata and processing status; it does not return the PDF bytes.

## List documents

`GET /documents?limit=20&offset=0` returns `items`, `total`, `limit`, and `offset`. Results are ordered newest first, with UUID as a deterministic tie-breaker. `limit` defaults to 20 (allowed range 1–100); `offset` defaults to 0 and must be nonnegative. Invalid query values return 422. An offset beyond the last row returns an empty `items` list while preserving the total count. Database errors return a generic 503.

```bash
curl 'http://localhost:8000/documents?limit=10&offset=0'
```

This is offset pagination: the next page uses `offset + limit`. Concurrent uploads can shift page boundaries; cursor pagination can be introduced if needed at scale.

### Search

`GET /documents?q=resume` keeps only documents whose **title, file name or category** contain every word of `q` (case-insensitive, any order, partial words match). `q` is at most 100 characters and at most 8 words count; a blank `q` lists everything. `%` and `_` are matched literally, not as wildcards. `total` reflects the search, so pagination works as usual, and it combines with `include_old_versions`. It is a plain database query: no AI request and no cost.

```bash
curl 'http://localhost:8000/documents?q=lease%20agreement'
```

## Local Redis

Start Redis from the repository root:

```bash
docker compose up -d --wait redis
docker compose exec -T redis redis-cli ping
```

The response should be `PONG`. Redis is bound to `127.0.0.1:6379` for local development. RQ uses Redis to store waiting jobs and worker state. PostgreSQL remains the source of document metadata. Uploads automatically submit extraction jobs to the `documents` queue.

Redis uses append-only persistence in the `redis_data` volume and `noeviction` to avoid silently evicting queue data. The default append-only fsync policy can lose roughly the last second of writes on a crash; this is development persistence, not an exactly-once job guarantee.

To start both supporting services, use `docker compose up -d --wait`. To stop them, use `docker compose stop`. Avoid `docker compose down -v` unless you intend to delete both database and Redis data.

## Run the background worker

Uploads return as soon as the file is saved and a job is queued; a separate worker process does the processing. With Redis running, open a terminal in `backend/`, activate `.venv` and start it:

```bash
source .venv/bin/activate
python -m app.worker
```

Leave it running to pick up jobs, or stop it with Ctrl+C. `python -m app.worker --burst` processes the waiting jobs and exits. Restart the worker after changing its code.

Without a worker, uploaded documents stay `queued`. `GET /health/queue` reports whether one is running (see below) and the web UI shows a notice when none is.

`app/tasks/queue.py` shares the Redis connection and queue between producers and workers. Set `REDIS_URL` in the root `.env` to override the local default. Jobs use JSON serialization on both sides. The worker uses RQ's `SpawnWorker`, which avoids unsafe forking on macOS; see the [RQ worker documentation](https://python-rq.org/docs/workers/#spawnworker).

### Queue health

`GET /health/queue` checks Redis and counts the workers listening on the `documents` queue:

```json
{"status": "ok", "redis": "connected", "workers": 1, "queued_jobs": 0}
```

`status` is `no_workers` (HTTP 200) when Redis is reachable but no worker is registered, so queued documents will not move. If Redis cannot be reached it returns 503. A worker that was killed without shutting down stays counted until its registration expires (a few minutes), so a recent crash can briefly still read as `ok`.

## Extract PDF text locally

From `backend/` with `.venv` active:

```bash
python -m app.processing.pdf_extraction "/absolute/path/to/document.pdf"
```

The command prints the page count, extracted character count, and a short text preview per page. It reads the existing file without saving extracted text or changing any document records. No API key or network request is involved.

`extract_pdf(Path(...))` returns a list of `ExtractedPage` objects, each containing `page_number` and `text`. Page numbers start at 1; blank pages remain in the list so later citations refer to the original PDF pages. Encrypted PDFs, unreadable PDFs, and PDFs with no readable text are rejected. A document with both text and blank/image pages keeps the empty pages; images inside a PDF that has text are not transcribed.

This uses [pypdf text extraction](https://pypdf.readthedocs.io/en/stable/user/extract-text.html), which does no OCR. Complex layouts may have imperfect reading order. A PDF with no text raises `NoTextError`, and the worker then reads it as images (see below). The upload worker also calls this helper to extract stored PDFs. The current helper has no page-count or decompressed-memory limit; the 10 MiB upload limit does not bound parsing memory.

Run extraction and upload tests with `python -m unittest discover -s tests -v`.

## Scanned PDFs and images

When a PDF has no text layer (a scan, or one made by "Microsoft Print to PDF"), or the upload is a PNG or JPG, the worker reads it with the vision model instead:

1. `app/processing/page_images.py` draws each PDF page (pypdfium2) or loads the picture (Pillow) and encodes it as a JPEG whose longest side is at most 2000 pixels. Transparent areas are flattened onto white. A picture needing more than 40 million pixels is refused before it is decoded.
2. `app/ai/ocr.py` sends each page to the model as an inline image, three at a time, asking for a plain transcription (nothing is stored by the provider, and the prompt treats the image as untrusted data). A page with no legible text becomes an empty page, and if no page has text the document fails with "No readable text found, even when the pages were read as images."
3. The pages continue through the normal chunking, embedding, summary and citation steps, so an answer cites the page of the scan it came from. A picture counts as page 1.

A scanned PDF with more than `OCR_MAX_PAGES` pages (default 10) fails with a message saying so; nothing is read partially. Each page is one paid request, logged as an `ocr` call with its tokens. Set `OCR_MODEL` to use a different vision model; it defaults to `ANSWER_MODEL`. A provider failure fails the document as "Document processing failed." and **Process again** retries it.

Documents that fail return the reason in `error_message` (`null` otherwise), and the interface shows it in the document's details.

## Extract an uploaded document in the worker

Apply the latest migration from `backend/` with the virtual environment active:

```bash
python -m alembic upgrade head
python -m app.cli.enqueue_document YOUR_DOCUMENT_UUID
python -m app.worker --burst
```

New uploads are queued automatically. For older uploads or recovery, use a document ID returned by `POST /documents`. The manual enqueue command submits extraction in Redis; the worker then reads the stored PDF and writes its pages to PostgreSQL. Alternatively, leave `python -m app.worker` running in another terminal. Check `GET /documents/{document_id}` for the resulting status.

With embeddings disabled, the lifecycle is `queued → processing → extracted`. With embeddings enabled, it is `queued → processing → embedded`. Invalid or unreadable documents become `failed`; the worker stores an error message and raises the error so RQ also records the failed job. A failed document can be queued again with the same command, with `POST /documents/{id}/reprocess` or with **Process again** in the web UI. `extracted` means text is available. `ready` is accepted by the schema and treated as searchable, but the current pipeline stops at `embedded`.

The `extracted_pages` JSONB column stores objects with `page_number` and `text`, including blank pages. This internal content is not returned by the metadata endpoints. A conditional database update claims each document before reading it, so duplicate jobs skip documents already processing or extracted. Unexpected worker termination can leave a document in `processing`; the next worker start (or a reprocess request) closes attempts older than twice the job timeout as failed and queues the document again. Keep the worker running for new uploads to process automatically.

To run the database integration tests alongside the unit tests (requires local PostgreSQL and migrations):

```bash
RUN_INTEGRATION_TESTS=1 python -m unittest discover -s tests -v
```

Integration tests create and delete their own document records and temporary files. Without the environment flag, these thirty-five tests are skipped. Downgrading the extraction migration discards extracted page data and changes `extracted` documents back to `queued`.

## Automatic queueing and queue failures

`POST /documents` saves the file, commits metadata in PostgreSQL, then enqueues extraction in Redis. The worker can therefore see the document as soon as it receives the job. HTTP 201 returns the initial `queued` metadata; poll `GET /documents/{document_id}` to see `processing`, `extracted`, `embedded`, or `failed`. With no worker running, jobs wait in Redis.

If Redis does not confirm enqueueing, the API returns HTTP 503 with `detail.message` and `detail.document_id`. The file and database record are preserved. The job may have been accepted before the connection failed, so check the returned document ID before retrying. If it remains `queued` after checking the worker, run `python -m app.cli.enqueue_document DOCUMENT_ID` instead of uploading another copy. Duplicate execution is guarded by the worker's database claim.

PostgreSQL and Redis do not share a transaction: an API crash after the database commit but before enqueueing can leave a saved document waiting without a job. The manual command is the current recovery path; a transactional outbox can close this gap later.

## Preview text chunks

From `backend/` with `.venv` active:

```bash
python -m app.processing.chunking "/absolute/path/to/document.pdf"
```

`chunk_pages(pages)` splits extracted pages into windows of at most 200 whitespace-separated words, with 40 words of overlap between adjacent chunks on the same page. These are word counts, not model token counts. Both sizes are configurable in Python. Overlap retains some context around window boundaries. Each chunk contains a zero-based `chunk_index`, the original one-based `page_number`, and `text`.

Chunks never cross pages. Blank pages produce no chunks, while subsequent chunks retain their original page numbers. Whitespace is collapsed to single spaces; words and punctuation are otherwise preserved. This simple first version can split sentences and does not reconstruct table structure. A final window that already reaches the end of a page does not produce redundant trailing windows.

The worker calls this helper and saves chunks alongside extracted pages. The preview command only prints chunks; it does not save them or make AI requests. The worker can optionally embed saved chunks.

## Stored document chunks

Apply the latest migration from `backend/` using `python -m alembic upgrade head`, then restart the worker. New uploads now extract pages, split them into chunks, and save both. Without embeddings, processing finishes at `extracted`; with embeddings enabled it continues to `embedded`.

`document_chunks` stores a UUID ID, document ID, zero-based chunk index, one-based page number, and chunk text. A foreign key links each chunk to its document and deletes associated chunks when the document is deleted. A unique constraint prevents duplicate positions within a document; its index also supports retrieving chunks for a document. Queries must explicitly order by `chunk_index` to reconstruct the original sequence.

The worker replaces any previous chunks on a retry. The replacement and extracted pages commit together, along with `extracted` when embeddings are disabled or `processing` when embedding continues. If saving fails, that transaction rolls back and the worker separately records `failed`. Previously saved content survives a failed replacement. Search will need to check document status before using stored chunks.

Documents already marked `extracted` before this migration are preserved without backfilling chunks. Those documents are not backfilled automatically; `POST /documents/{id}/reprocess` builds their chunks and embeddings on request. The metadata API still returns the same fields. Embeddings are optional as described below; document similarity search is available as described below.

Downgrading this migration deletes the chunk table and its contents while preserving document records and extracted pages.

## Embedding client

`app.ai.embeddings.generate_embeddings(texts)` sends a list of text strings to OpenAI and returns an `EmbeddingBatch` containing `vectors` in the original input order, the returned model name, and the input token count. It uses `text-embedding-3-small` with 1,536 dimensions. See the [official OpenAI embeddings guide](https://developers.openai.com/api/docs/guides/embeddings).

To use the AI features, set `OPENAI_API_KEY` in the repository root `.env` (ignored by Git). No key is needed to start the API, extract PDFs, create chunks, or run the mocked embedding tests. The supplied assignment key is configured only in the ignored local `.env`; repository clones must supply their own key.

The helper accepts up to 64 texts per request, rejects blank inputs, and returns an empty batch without an API request for empty input. It checks response positions, vector dimensions, and finite values before returning. Requests have a 30-second SDK timeout and up to two SDK retries. Provider errors propagate to the caller for handling by the later pipeline integration.

These limits count texts, not tokens; input token limits are still enforced by the provider. The caller will need to split larger batches and handle texts exceeding the model token limit. Word-based chunks do not guarantee a token bound. Importing the module makes no API request; calling the helper with nonempty text does send that text to the provider and may incur charges.

The worker can call this helper and store vectors when explicitly enabled. All embedding tests mock the SDK: `python -m unittest discover -s tests -v` makes no OpenAI requests. A separate live SDK smoke check succeeded with `text-embedding-3-small`: one short synthetic input, 1,536 dimensions, and 5 input tokens. A subsequent live upload also verified the full worker pipeline: 4 extracted pages, 6 chunks, and 6 saved vectors, with 1,240 input tokens reported by the completed job.

## Vector storage with pgvector

The vector-storage migration enables the PostgreSQL `vector` extension and adds nullable `embedding vector(1536)` and `embedding_model` columns to `document_chunks`. Apply it from `backend/` with `python -m alembic upgrade head`. The existing Docker image already includes the extension binaries; enabling the extension installs its SQL types and operators in this database. The migration needs a database role permitted to create the extension; the local Compose database owner has that access.

A chunk without an embedding has both new columns set to NULL, so existing documents and the extraction worker continue to work. When storing a vector, its model name must be stored with it. PostgreSQL enforces 1,536 dimensions, and a check constraint enforces the vector/model pair. Future search must use the same embedding model and dimensions for document chunks and query text.

The Python `pgvector` package provides SQLAlchemy's `VECTOR` type and distance operations. The integration tests verify round-trip storage, cosine-distance ordering, dimension enforcement, and vector/model consistency using synthetic vectors. These tests roll back their fixture transactions and make no AI calls. See the [official pgvector Python integration](https://github.com/pgvector/pgvector-python#sqlalchemy).

No approximate vector index is added yet; initial similarity queries can use exact scans for this small local dataset. The worker generates embeddings only when enabled; this migration does not backfill vectors. Downgrading removes the two columns and their check constraint, preserving chunk text and leaving the shared vector extension installed.

## Optional embeddings in the background worker

Apply migrations with `python -m alembic upgrade head`. When `ENABLE_EMBEDDINGS` is unset, embeddings run exactly when `OPENAI_API_KEY` is set; without a key, uploaded documents finish at `extracted` without any AI calls. An explicit `ENABLE_EMBEDDINGS=true` or `false` always wins. To force the embedding stage on, configure the root `.env`:

```dotenv
OPENAI_API_KEY=your_key_here
ENABLE_EMBEDDINGS=true
```

Restart the worker after changing configuration. Do not commit `.env`. Enabled processing sends chunk text to OpenAI and can incur charges. The supplied assignment key was configured locally and verified with one small live embedding request. Automatic embedding generation is now enabled in the local `.env` after a successful end-to-end check; `.env.example` continues to default to `false` for fresh clones. Automated tests still use mocks only.

The worker commits extracted pages and chunks first, keeping status `processing`. It then requests embeddings in batches of at most 64 chunks, outside database transactions. After all batches succeed, it writes all vectors with their model names and sets `embedded` in a single transaction. A provider or vector-save failure marks the document `failed`; extracted text remains saved and no partial vector updates are committed. Missing credentials with embeddings enabled also fail processing.

`embedded` means vectors are stored; it does not mean a summary or chat answer exists. `ready` remains reserved for the later complete pipeline. The RQ result includes `embedding_input_tokens` from successful batches; this is temporary job-result data. New processing attempts also persist observed token usage as described below; neither is a complete billing ledger or accounts for all failed requests and SDK retries.

A manual retry of a failed document re-extracts and replaces its chunks, then repeats embedding requests if enabled. Successful provider batches can therefore be charged again after a later failure. Existing `extracted` documents are not reprocessed automatically; use `POST /documents/{id}/reprocess` (or **Process again** in the UI) to embed them. A worker killed mid-job is recovered when a worker next starts.

## Search a document by meaning

`POST /documents/{document_id}/search` accepts a question and returns the closest stored chunks for that document. The document must be `embedded` or `ready`, with vectors generated by the supported embedding model. Use the ID returned by a live-enabled upload.

```bash
curl -X POST "http://localhost:8000/documents/YOUR_DOCUMENT_UUID/search" \
  -H "Content-Type: application/json" \
  -d '{"question":"Which libraries are recommended for document chat and embeddings?","top_k":3}'
```

You can also use the **search** section at `http://localhost:8000/docs`. The question is trimmed, must contain 1–2,000 characters, and `top_k` defaults to 8 (allowed range 1–20). Each match includes `chunk_id`, `chunk_index`, `page_number`, `text`, and `cosine_distance`. Results are sorted by increasing distance, with chunk index breaking ties. Lower distance means a closer vector match; it is not a probability or confidence score.

The endpoint checks document readiness before making an API call, embeds the question once, then compares it with compatible vectors from the selected document. The query and stored chunks must use the same model. No database transaction remains open during the provider call. Missing documents return 404, unavailable/incompatible embeddings return 409, and invalid inputs return 422. Database or provider availability problems return generic 503 responses; an invalid embedding response returns 502.

Search makes a paid embedding request for the question; it does not re-embed the document or generate an answer. It returns up to `top_k` nearest chunks even if the question is unrelated—there is no relevance threshold yet. Retrieval quality, answer grounding, and abstention need ongoing evaluation as the answer endpoint is expanded. Similarity queries currently use exact vector scans rather than an approximate index.

A live check against the embedded case study returned HTTP 200 and ranked a relevant page 3 chunk first for the example question. All automated search tests use synthetic vectors and mocked question embeddings; tests cover document/model filtering, ranking, limits, readiness, and safe errors.

## Ask a document with source citations

`POST /documents/{document_id}/ask` accepts the same request as search:

```json
{
  "question": "Which libraries are recommended for document chat and embeddings?",
  "top_k": 3
}
```

Use an embedded document ID in the **answers** section of Swagger at `http://localhost:8000/docs`. The endpoint embeds the question, retrieves relevant chunks, and sends those chunks to an answer model. It returns `answer`, `insufficient_evidence`, `citations`, the actual answer model name, and generation input/output token usage. Each citation has a `source_number` matching an inline label such as `[1]`, plus a stored chunk ID, original page number, and source text.

Chat answers use `gpt-4.1` by default (a stronger model than the one for summaries and other generated content, because a wrong detail does the most harm in an answer); set `CHAT_MODEL` in the root `.env` and restart the API to use another model available to the supplied key, for example `gpt-4.1-mini` for lower cost. It uses the [OpenAI Responses API with structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs), a maximum of 1,500 output tokens, a 30-second SDK timeout, up to two SDK retries, and `store=False`. This setting is not a claim of zero provider retention. Each question incurs a query-embedding request and an answer-generation request. Returned usage covers generation only, excluding query embedding and retries; it is not a durable billing record.

The model is instructed to use only provided sources, treat document text and questions as untrusted data rather than instructions, and decline when sources do not support an answer. The server validates that inline citation numbers match the declared source list and refer to retrieved chunks; citation IDs, pages, and text are filled from retrieval rather than generated metadata. Invalid, incomplete, or refused structured output returns a generic 502. Provider/configuration failures return 503. Search readiness/validation errors retain their existing status codes.

When the model reports insufficient evidence, the server returns a fixed explanatory answer with no citations. These checks validate citation references, not whether every claim is entailed by its source. Prompt injection resistance, retrieval coverage, and unsupported-claim detection still require broader evaluation. In particular, retrieval may omit relevant information elsewhere in the document.

A live question about recommended document-chat and embedding libraries returned a citation to page 3. A live question about an exact company revenue figure absent from the document returned insufficient evidence without citations. Automated tests use mocked provider output and verify citation mapping, invalid citation rejection, incomplete responses, abstention, and safe API errors. The `/ask` endpoint remains stateless and does not change document processing status. Use the conversation endpoints below for persisted follow-up context.

## Saved document conversations

Apply the latest migration from `backend/` with `python -m alembic upgrade head`, then restart the API. Use these routes in the **conversations** section of Swagger:

1. `POST /documents/{document_id}/conversations` creates an empty conversation for a searchable document (HTTP 201); save its returned `id`.
2. `POST /conversations/{conversation_id}/messages` sends a question with `{"question":"Which libraries are recommended?","top_k":3}` and returns a saved turn (HTTP 201).
3. Send a follow-up to the same messages endpoint, such as `{"question":"Which of those are for document chat?"}`.
4. `GET /conversations/{conversation_id}?limit=20&offset=0` retrieves persisted turns in order, with `total`, `limit`, and `offset`. Limit allows 1–100; offset must be nonnegative.

A conversation created here belongs to one document (conversations across several documents are described under Multi-document chat below). A turn stores the complete question/answer response, including citation snapshots, model name, and generation token usage. Question and answer are stored as one paired turn; unsuccessful generation does not leave a partial user message. PostgreSQL saves each turn and updates its conversation count in the same transaction. Deleting a document cascades through its conversations and turns.

For each follow-up, the server loads the latest three turns, in chronological order, clipping each historical question to 1,000 characters and answer to 2,000. All turns remain stored, but only this bounded context is sent to the answer model. Retrieval runs twice: once for the question as asked, and once for the question followed by up to 400 characters of the latest prior question and 300 of its answer. The two rankings are merged by reciprocal-rank fusion, so a passage found by both ranks first and up to 1.5 × `top_k` passages are kept. Using only the combined text drags the old topic into a change of subject; using only the bare question misses "and the second one?". This avoids an extra model request for question rewriting; references to older turns may require a better rewrite or memory strategy later.

History is provided as untrusted context to resolve references, not as factual evidence. New answers must cite currently retrieved document chunks; prior answers and their citation labels cannot supply evidence. Each message still makes query-embedding and generation requests, and the bounded history increases generation input usage.

No database transaction is held open during AI requests. An optimistic version check detects simultaneous messages based on the same history; one request succeeds and a conflicting request returns 409 without appending a stale answer. The conflicting request may already have incurred provider usage. Fetch history before retrying; request-ID deduplication is not implemented yet. Database persistence errors return 503, and provider/answer validation errors preserve the existing safe error behavior.

A live two-turn conversation verified that a follow-up referring to “those” used the previous turn and returned a page 3 citation. Both completed turns were fetched from PostgreSQL through the history route. Automated tests mock provider calls and cover persistence, context limits, failure cleanup, concurrent-update conflicts, and cascading deletion. Downgrading the conversation migration deletes conversation history while preserving document records.

## Generate and read a saved summary

Use the **summaries** section in Swagger:

- `POST /documents/{document_id}/summary` generates a short summary of the extracted text and stores it in the existing `documents.summary` column. If a summary already exists, it returns that value without another provider request.
- `GET /documents/{document_id}/summary` reads the saved summary without making an AI request. A missing document or a summary not yet generated returns 404.

Both routes return `document_id` and `summary`. Summary generation requires extracted pages and status `extracted`, `embedded`, or `ready`; unavailable text returns 409. This feature does not change document processing status or automatically run on upload. No new migration is needed because the initial document table already included the summary column.

The generator uses the complete extracted text, normalizes whitespace, and retains page labels in the prompt. It rejects input exceeding 60,000 characters with 413 instead of silently truncating it. Larger documents will need a later multi-stage summarization strategy. The model is instructed to summarize only the supplied text, treat embedded instructions as untrusted data, and write one concise paragraph covering the document's purpose and key information. Outputs must be completed, nonblank, and no longer than 4,000 characters; invalid/incomplete/refused responses return 502.

Generation uses `ANSWER_MODEL` (default `gpt-4.1-mini`), structured output, at most 800 output tokens, a 30-second SDK timeout, up to two SDK retries, and `store=False`. It sends document text to OpenAI and may incur charges. The saved summary is plain text without citations or persisted generation-usage metadata. Factual accuracy still requires evaluation; generation is not proof that every statement is supported.

No database transaction stays open during the provider call. If two requests generate concurrently, the first stored summary is preserved and returned to both; both requests may incur provider usage. Generation failures do not clear an existing summary or change document status. Provider/configuration failures return 503. There is no forced-regeneration endpoint yet.

A live check generated a summary for the embedded case study, verified it in PostgreSQL, and confirmed identical results from GET and a repeated POST. Automated tests use a mocked provider and cover persistence, caching, unavailable text, input/output limits, failure handling, and concurrent-save behavior.

## Document statistics

`GET /stats/documents` (the **statistics** section in Swagger) returns:

- `total_documents` and a `by_status` count for each supported status, including zeros.
- `total_storage_bytes`: sum of the recorded original PDF upload sizes.
- `documents_with_summary`: documents with a stored non-NULL summary.
- `total_extracted_pages`: number of stored extracted page entries, including blank pages.
- `total_chunks` and `chunks_with_embeddings`: stored chunk rows and rows with non-NULL vectors.

```bash
curl http://localhost:8000/stats/documents
```

All values come from one PostgreSQL SELECT so they share a statement snapshot. Separate scalar chunk subqueries avoid multiplying document counts or byte totals when a document has several chunks. An empty dataset returns zeros, and database failures return a generic 503. This endpoint makes no Redis or AI requests and requires no migration.

Storage bytes are metadata totals, not a filesystem scan or the total disk space used by PostgreSQL, vectors, extracted text, Redis, or orphan files. Page/chunk/vector totals include retained content on failed documents and are not counts of searchable content. The status counts describe current document state rather than historical job attempts; processing duration metrics are available from the endpoint below.

The live local check returned 3 documents, 388,410 recorded PDF bytes, 8 extracted pages, 6 chunks, 6 vectors, and 1 summary. Statistics tests use temporary PostgreSQL tables to test empty and populated datasets without deleting or modifying user documents.

## Processing attempt metrics

Apply migrations with `python -m alembic upgrade head` from `backend/`, then restart the API and worker. `GET /metrics/processing` aggregates retained processing attempts:

- `total_attempts`, `processing`, `succeeded`, and `failed`.
- `success_rate`: succeeded divided by completed attempts, from 0 to 1; null when none have completed.
- `average_duration_ms`, averages for success/failure separately, and `max_duration_ms`; null when no matching duration exists.
- `observed_embedding_input_tokens`: sum of usage returned by successful embedding batches and persisted when attempts finish, including batches preceding a later failure.

```bash
curl http://localhost:8000/metrics/processing
```

The worker creates a `processing_attempts` row in the transaction that claims a queued/failed document. Duplicate jobs that skip processing do not create attempts. Each retry gets a separate row, so one document can have both failed and successful attempts. Successful completion and final document state commit together; ordinary failures record a safe error and failed outcome together. Completion constraints require a nonnegative duration and finish timestamp for terminal outcomes. The RQ result includes the attempt UUID for tracing.

Durations use Python's monotonic performance clock from the start of the handler through its completion-record update, rounded to milliseconds. They exclude time waiting in Redis and do not measure upload, search, chat, summary generation, or the final database commit acknowledgment. A successful extraction-only job counts as succeeded, as does successful processing with embeddings. The live extraction-only check recorded one succeeded attempt at 129 ms with zero embedding tokens; this is a functional check, not a performance benchmark.

Metrics begin with this migration and worker update; earlier jobs are not backfilled. A force-killed worker or unavailable database can leave an attempt marked `processing`, just as it can leave the document processing state unfinished. An attempt left that way is closed as failed, and its document queued again, when a worker next starts or the document is reprocessed (once it is older than twice the job timeout). Observed token usage is not an invoice: it omits unknown provider usage, failed request/retry charges, and other API features; active attempts are not updated incrementally. Deleting a document cascades to its attempts, so aggregates describe retained history. Downgrading removes attempt history without deleting documents.

This metrics endpoint performs one aggregate PostgreSQL query and makes no AI requests. Tests verify successful and failed runs, retry history, duplicate skips, observed batch usage, empty aggregates, duration calculations, completion constraints, and safe database errors.

## Generate and read key insights

Apply the latest migration with `python -m alembic upgrade head` from `backend/`, then restart the API. Use the **insights** section in Swagger:

- `POST /documents/{document_id}/insights` generates and saves key takeaways. A previously saved result is returned without another AI request.
- `GET /documents/{document_id}/insights` reads the saved takeaways without an AI request; missing documents or ungenerated insights return 404.

Each result contains `document_id` and an `insights` list. An insight contains `text`, its original `page_number`, and an `evidence` excerpt. Results are stored in the document's nullable JSONB `insights` column. Generation requires extracted text and status `extracted`, `embedded`, or `ready`; otherwise it returns 409. This endpoint does not run automatically on upload or change document status.

The server normalizes extracted whitespace and creates numbered source excerpts of at most 240 characters, splitting at spaces when possible and retaining original page numbers. Blank pages produce no excerpts. The model proposes short insights and selects a supporting excerpt ID; it does not generate the quote or page metadata. The server rejects invalid IDs, empty/oversized insight text, incomplete responses, or result counts outside 1–6, then copies the source excerpt and page directly into the response. The prompt requests 3–5 distinct takeaways when supported.

The serialized full excerpt input is limited to 60,000 characters, including source metadata. Larger inputs return 413 without an API call or silent truncation; long-document insight extraction remains a future extension. Requests use `ANSWER_MODEL` (default `gpt-4.1-mini`), structured output, at most 1,200 output tokens, a 30-second SDK timeout, up to two SDK retries, and `store=False`. Generation sends text to OpenAI and may incur charges. Repeated reads are cached; simultaneous first-generation requests can both incur usage, but the first saved result is preserved. Usage metadata is not persisted for this feature yet.

Source IDs ensure excerpts and page references are real; they do not prove that the insight's entire claim is entailed by that excerpt. Factual entailment, extraction boundaries, and prompt-injection resistance need ongoing evaluation. Generation errors preserve stored document state and return safe 502/503 responses. No database transaction remains open during the AI request.

A live check generated five insights for the case study, verified that every excerpt occurs on its referenced page, and confirmed cached GET and POST results. Automated tests cover source-ID mapping, text coverage across excerpt windows, invalid output, limits, caching, failure cleanup, and concurrent-save behavior. Downgrading removes stored insights while preserving documents, summaries, chunks, and chat history.

## AI usage and estimated cost

`GET /metrics/ai-usage` (the **metrics** section in Swagger) returns token usage and an estimated cost in US dollars:

- `chat`: one row per answer model, summed from the `model`, `input_tokens` and `output_tokens` saved with every conversation turn.
- `embeddings`: input tokens summed from processing attempts, priced for `text-embedding-3-small`.
- `estimated_total_cost_usd`: sum of every priced row. Models without a known price appear in `unpriced_models` and are left out of the total.
- `not_persisted`: usage that is not stored in the database (summaries, insights, stateless `/ask` answers, and query embeddings).

Prices live in `backend/app/core/pricing.py` as per-million-token estimates and match dated model snapshots such as `gpt-4.1-mini-2025-04-14`. They are estimates, not billing data; check them against the provider's price list. The endpoint reads only PostgreSQL and never calls the AI provider.

Cost optimization already in place: embeddings are sent in batches of 64 chunks, summaries and insights are generated once and reused, chat sends only the retrieved chunks plus the latest three turns, and answers use a small model with an output-token cap.

## Rate limits and quotas

Endpoints that spend provider money are limited per client IP with fixed-window counters in Redis:

| Scope | Endpoints | Default |
| --- | --- | --- |
| `ai` | `POST /documents/{id}/ask`, `POST /conversations/{id}/messages`, `POST /conversations/{id}/messages/stream`, `POST /documents/{id}/suggested-questions`, `POST /documents/{id}/summary`, `POST /documents/{id}/insights` | 20 per minute and 500 per day |
| `upload` | `POST /documents` | 10 per minute |

An exceeded limit returns HTTP 429 with a `Retry-After` header (seconds until the window resets) and a message naming the rule. Rejected requests still count toward the window. Configure with `AI_RATE_LIMIT_PER_MINUTE`, `AI_DAILY_QUOTA` and `UPLOAD_RATE_LIMIT_PER_MINUTE` (0 disables a rule) or turn everything off with `RATE_LIMIT_ENABLED=false`; restart the API after changing them. Reads, health checks, statistics and metrics are not limited.

Design choices: the limiter fails open and logs `rate_limiter_unavailable` if Redis is down, because a limiter outage should not take the API offline. Clients are identified by the direct peer address, so behind a reverse proxy the proxy address would be shared by everyone; trusting `X-Forwarded-For` needs a known proxy and is not enabled. Counters are per client, not per user, because the app has no accounts.

## Logging and observability

Every process logs JSON lines to stderr (set `LOG_LEVEL` to `DEBUG`, `INFO`, `WARNING`, `ERROR` or `CRITICAL`). Events:

- `request` / `request_failed`: method, path, status, duration and client. Each response carries an `X-Request-ID` header; a safe client-supplied ID is reused, otherwise one is generated, and every log line written while handling that request includes it.
- `ai_call`: operation (`embeddings`, `answer`, `summary`, `insights`), model, input and output tokens, duration. This is where summary and insight usage can be audited, since it is not stored in the database.
- `document_processing_started` / `_finished` / `_failed` / `_skipped` from the worker, with document and attempt IDs, page and chunk counts, tokens, duration, and the traceback for failures.
- `rate_limit_exceeded` and `rate_limiter_unavailable`.

Logs contain identifiers, sizes, durations, token counts and outcomes, not document text, questions or answers. Failure tracebacks can include provider error text, so keep logs private. For monitoring, `/health`, `/health/db`, `/stats/documents`, `/metrics/processing` and `/metrics/ai-usage` cover liveness, database reachability, document pipeline state, job timings and spend. Run uvicorn with `--no-access-log` to avoid duplicate request lines.

## Retry and recovery

`POST /documents/{document_id}/reprocess` (HTTP 202) queues processing again and returns the document with status `queued`. It works for:

- `failed` documents (the error message is cleared),
- `queued` documents whose job was never confirmed (for example Redis was down at upload),
- `extracted` documents, which backfills embeddings after you add an API key,
- `processing` documents whose worker died: an attempt running longer than 10 minutes (twice the 5-minute job timeout) is closed as `failed` in the processing metrics and the document is queued again.

A document that is `embedded`/`ready`, or genuinely still processing, returns 409 and nothing is queued. If the job queue is unavailable the document stays `queued` and the call can simply be repeated (503). The endpoint shares the `upload` rate limit because reprocessing can spend embedding tokens.

When a worker starts it also re-queues every abandoned document, so a crash or restart heals itself without a manual call. A duplicate job is harmless: only one worker can claim a `queued` document, and the other skips it.

## Query efficiency

Extracted pages and insights can be megabytes per document. Listing, retrieving, and searching documents defer those columns, and summary or insight routes load only the column they use, so metadata lookups no longer transfer document text.

## Automatic summary and insights

When a document finishes embedding, the same worker job generates its summary and key insights, so a freshly processed document already has an overview and takeaways with page evidence. This follows `ENABLE_EMBEDDINGS` unless `AUTO_GENERATE_CONTENT` is set to `true` or `false`.

- **Never fails the document.** Generation runs after the processing attempt is recorded as succeeded. If it fails (provider error, a document over the 60,000-character limit, and so on), the document stays `embedded`, the worker logs `auto_generation_failed` with a safe reason, and `POST /documents/{id}/summary` or `/insights` still work on demand.
- **Independent.** A failing summary does not stop insights from being generated, and the reverse.
- **No duplicate cost.** Existing saved content is reused, and a user clicking Generate while the worker is still running at worst triggers one extra call; the first saved result wins.
- **Cost.** One extra call each for the summary and insights; for the 4-page case study that was about 1,600 and 1,900 input tokens (under $0.002). Both appear as `ai_call` log events. Their tokens are not stored in the database, so `/metrics/ai-usage` does not include them.
- **Timing.** Status becomes `embedded` (Search ready) first, so chat is available a few seconds before the summary and insights appear; the document view's refresh buttons pick them up. These calls run inside the same 5-minute job timeout, and the processing duration metric excludes them.

## List a document's conversations

`GET /documents/{document_id}/conversations?limit=20&offset=0&has_turns=false` returns the document's conversations newest first with `id`, `document_id`, `created_at` and `turn_count`, plus `total`, `limit` and `offset`. Pass `has_turns=true` to skip conversations that were created but never answered. An unknown document returns 404. The endpoint reads PostgreSQL only and never calls the AI provider. The frontend uses `limit=1&has_turns=true` to restore the latest conversation when a document is opened; fetch its turns with `GET /conversations/{id}`.

## API latency metrics

`GET /metrics/api` returns request counts and latency per route for the API process since it started: `since`, `total_requests`, `server_error_rate` (5xx share, `null` before any request) and a `routes` list sorted by traffic. Each route has `method`, `route`, `requests`, `server_errors`, `average_ms`, `p95_ms` and `max_ms`.

Routes are grouped by template (`/documents/{document_id}`) rather than the raw path, and unmatched paths share one `unmatched` entry, so memory stays bounded however many URLs are requested. The 95th percentile uses nearest rank over each route's most recent 1,000 requests; counts, averages and the maximum cover every request. Statistics live in memory, so they reset when the API restarts and each API process reports only its own traffic. The JSON request log (`request` events with `duration_ms`) is the durable record, and job durations are stored in `processing_attempts` (see `/metrics/processing`).

## Query embedding cache

Search, ask and conversation messages embed the question before searching. The vector is cached in Redis under `embedding:{model}:{dimensions}:{sha256}` where the hash covers the question with case and whitespace normalised, so `Leave  POLICY?` and `leave policy?` share an entry. Entries expire after `EMBEDDING_CACHE_TTL_SECONDS` (default 86400; 0 disables the cache). A cache hit makes no provider call. Redis errors and corrupt entries are logged and fall back to the provider, so the cache can never fail a request. Chat answers are not cached because they depend on the conversation history. Hits and misses appear in the JSON log as `embedding_cache` events.

## Suggested questions

`POST /documents/{document_id}/suggested-questions` returns 3–4 starter questions (`questions`, plus `cached`) built from the document's saved summary and insights, not its full text, so the request is small. It returns 409 until at least one of them exists. The result is cached in Redis for 7 days under a hash of the model, summary and insights, so repeating the call is free and editing the content produces fresh suggestions. A Redis outage only costs a regeneration. The endpoint uses the `ai` rate limit. The chat panel shows it as a **Suggest questions** button; choosing a suggestion fills the question box without sending it.

## Streaming chat answers

`POST /conversations/{conversation_id}/messages/stream` takes the same body as `/messages` and responds with `text/event-stream`. Events:

| Event | Data | Meaning |
| --- | --- | --- |
| `delta` | `{"text": "..."}` | Next piece of the answer text. A preview only. |
| `turn` | the saved turn, same shape as the `/messages` response | Final event. Contains the validated answer, citations and token usage; clients should show it instead of the streamed text. |
| `error` | `{"detail": "...", "status": 502}` | Generation or saving failed after streaming began. |

To edit a question, send the new text with `"replace_turn": N` (to either messages endpoint; `N` is a turn number from 1). The answer is generated as if turn `N` had not happened: only turns before `N` are used as context. When it is saved, turn `N` and every turn after it are deleted and the new turn is saved as number `N`, in one transaction, so the conversation never holds a mix of old and new. If generation fails, nothing is deleted. A `replace_turn` beyond the current turn count returns 409, and the version check also returns 409 if another message was saved meanwhile. Edited-out turns are gone for good; there is no undo.

Problems found before generation starts (unknown conversation 404, document not searchable 409, retrieval or database failure 503) return a normal HTTP error because the status line has not been sent yet. The turn is saved only after the complete answer passes citation validation, so a dropped connection or an `error` event leaves the conversation unchanged and the question can be asked again. The version check and rate limit are the same as `/messages`.

Implementation: the model returns structured JSON with `answer` first, and the server decodes the `answer` string from the raw JSON deltas as they arrive. Request latency in `/metrics/api` measures time to the first byte for this route, not the full stream.

## Citation validation

The server requires at least one citation, each within the retrieved sources; the `[n]` labels written in the answer text decide which sources are attached (their page and quote come from the stored chunks, never from the model). When the text has no label at all but the model's `source_numbers` are valid, those are used and their labels are appended to the answer (short factual answers often come back this way, and asking again rarely changes it). If a label or declared source does not exist, or none is given, the request is retried once; a streamed answer falls back to a regular request. A second failure returns 502 and nothing is saved. In a live comparison on a sample document this took successful answers from 1 of 8 to 8 of 8, because the previous prompt and strict cross-check often rejected valid answers.

## Custom summaries

`POST /documents/{document_id}/summary/custom` writes a summary in a chosen style. Body (all fields optional):

| Field | Values | Default |
| --- | --- | --- |
| `length` | `short` (at most 3 sentences), `medium` (one paragraph), `long` (two or three short paragraphs) | `medium` |
| `tone` | `neutral`, `formal`, `casual`, `executive` | `neutral` |
| `focus` | free text up to 200 characters, such as `deadlines and costs` | none |

The response has `summary`, the `options` used and `cached`. A custom summary is **not saved on the document**: the document keeps one default summary (`/summary`). Variants are cached in Redis for 7 days under a hash of the model and options, so repeating a style returns `cached: true` without a provider call. The `focus` text is sent as data next to the document, never inside the instructions, and the prompt tells the model to treat it as a preference only and to say so briefly when the document has little on the topic. Uses the `ai` rate limit; returns 409 until text is extracted.

## Answer accuracy

What was changed to make chat answers more accurate, and why:

- **More passages.** The default is 8 (it was 3), so lists and longer explanations are not cut short. The web app no longer sends its own `top_k`.
- **Follow-ups** search both the bare question and the question with the previous turn, fused (see the conversation section above).
- **Every-document questions** take the best passages of each document and group them by document (see multi-document chat).
- **Cleaner text.** Extraction and chunking join accents written before their letter (`B¨orm` becomes `Börm`), spell ligatures out (`ﬁ` becomes `fi`) and drop NUL characters. Chunks keep their line breaks, so a bullet stays under its heading.
- **Prompt rules.** Keep each fact with the heading it follows, copy names, numbers and dates exactly, name documents rather than calling them "Document 1", answer the supported part of a question and say what is missing, and read through broken PDF spacing.
- **False premises.** A question can assume something the documents never say ("the Node.js server" when they describe FastAPI). The model is told to say the sources do not mention it, then give what they do say, and never to repeat the unsupported term as fact. It is also told that earlier answers in the history can be wrong: when the user challenges one, it checks the sources and corrects it plainly instead of defending it.
- **Repairs after the model answers.** Accented names the model mangled are restored from the sources (`Bõrm` becomes `Börm`), and control characters are removed (PostgreSQL cannot store NUL; one in an answer used to make saving the turn fail).
- **Retries with a fallback model.** When the model's structured output is cut off (it sometimes loops while writing the citation list, and the provider's content filter can stop the stronger model on long verbatim passages), the question is asked once more with `ANSWER_MODEL`, since asking the same model again would stop in the same place. The prompt also asks for explanations in the model's own words, which avoids most of those stops.
- **A stronger chat model**, `gpt-4.1` by default (`CHAT_MODEL`); in side-by-side checks it kept one employer's bullets apart from another's where `gpt-4.1-mini` did not. It costs about five times as much per answer (a few tenths of a cent).
- **Failures are logged** with their real cause (`conversation_failed`); clients still get a short, safe message.

Documents uploaded before the text cleaning keep their old chunks until their text is chunked again.

## Category

Each document can carry one `category`: a short label of one to three words (for example `Resume`, `Lease Agreement` or `Technical Design`), chosen freely by the model and saved on the document. There is no fixed list. The server tidies the label (whitespace, stray punctuation) and rejects one longer than 40 characters. There are no tags.

- `POST /documents/{document_id}/classification` generates and saves the category and title (or returns the saved result, with no provider call). `GET` on the same path reads them and returns 404 until a category exists. The workers also do this automatically after the summary and insights, as a best-effort step that can never fail the document.
- The source is the saved summary and insights (a small request). Documents with neither fall back to the first 4,000 characters of text.
- Documents include `category` (nullable until classified) and `title` (see below). The category is searchable through `GET /documents?q=` (see **Search** above).

Migration `b7d3e1a94c20` added the category and tag columns; migration `f8b3c5d19a27` removed tags and the category index, leaving the free-form `category` column. Existing documents keep the category they already had; ones with none stay unclassified until `POST /classification` is called or they are reprocessed.

## Document titles

File names such as `System_ Case Study.pdf` read badly, so a document can carry a `title` (up to 120 characters) and a `title_source` (`ai` or `user`). Both are `null` until one is set, and clients then show the file name.

- **AI titles cost nothing extra.** The classification request that picks the category also writes a title of at most 10 words (a missing or unusable title never fails classification). The workers do this automatically with the summary and insights. A document classified before titles existed is asked once, for its title alone, the next time `POST /documents/{id}/classification` is called; its category is left as it was.
- `PATCH /documents/{document_id}` with `{"title": "Q3 Plan"}` sets a title and marks it `user`; `{"title": null}` (or blank) clears it so the file name shows again. Whitespace is tidied, titles over 120 characters get 422, and an unknown document gets 404. It returns the document and publishes `document.updated`.
- **A person's title always wins.** The AI never replaces a `user` title, and renaming applies to every version of the document, because the title names the document, not one file. A new version inherits a `user` title; an `ai` title is written afresh from the new version's content.
- Versions and the classification response include `title`. Citations and comparison results still name the source file.

Migration `e6f1a4c92d58` adds the two nullable columns (and a check that `title_source` is `ai` or `user`).

## Document versions

A document can have several versions. Each version is a normal document of its own (its own file, processing, embeddings, summary, insights, category and chats), linked to the others by a shared `group_id`. The first upload is version 1 and its id names the group.

- `POST /documents/{document_id}/versions` takes a PDF as multipart `file` (same rules and `upload` rate limit as `POST /documents`) and creates the next version, returning it with HTTP 201 and queueing processing. The id of any version works.
- `GET /documents/{document_id}/versions` lists every version, newest first: `id`, `version_number`, `filename`, `size_bytes`, `status`, `is_latest` and `created_at`.
- Documents carry `group_id`, `version_number` and `is_latest`. `GET /documents` lists **only the latest version** of each document; add `include_old_versions=true` to list them all. Counts in `/stats/documents` include every version.
- A file with the same SHA-256 as the current latest version is rejected with 409 and stored nowhere, so re-uploading the same file does not create a duplicate version.
- Version numbers are unique per group; if two uploads race for the same number, one gets 409 and nothing is left behind (the file is removed and the previous latest version stays latest).

Uploading a new version never changes or removes an older one, so a conversation always refers to the exact file it was asked about (older versions go away only when someone deletes them, see below). Migration `c4e8f2b17d35` turns every existing document into version 1 of its own group.

## Deleting documents

`DELETE /documents/{document_id}` returns 204 and permanently removes a document:

- Its chunks and embeddings, saved chat conversations, processing attempts and stored PDF go with it. The summary, insights and category live on the document row and go too.
- A multi-document conversation that included it is deleted as well (its answers quote the deleted file); the other documents are untouched.
- By default only that version is deleted. Deleting the newest version makes the one before it current again. Add `?all_versions=true` to delete every version of the document (the id of any version works). The web UI uses this.
- A document a worker is processing right now returns 409 and nothing is deleted; try again when it finishes. A job abandoned by a dead worker does not count as running.
- A queued job for a deleted document is skipped by the worker, not failed. The PDF is removed after the database commit, and a failure to remove it is logged, not returned.
- Statistics, processing metrics and `GET /metrics/ai-usage` are computed from stored rows, so they stop counting a deleted document, its attempts, its chats and the tokens they used. Estimated spend can therefore go down after a deletion.

Deletion cannot be undone. There is no authentication in this project, so anyone who can reach the API can delete documents.

## Multi-document chat

A conversation can span two to ten documents. Answers and citations name the document each passage came from.

- `POST /multi-conversations` takes `{"document_ids": [...]}` (2–10 distinct ids, each already searchable, otherwise 404 or 409) and returns a conversation with `document_id: null` and the `document_ids` it covers.
- `GET /multi-conversations` lists them, newest first (`limit`, `offset`, `has_turns`).
- Messages use the **same endpoints** as single-document chat: `POST /conversations/{id}/messages`, `.../messages/stream` and `GET /conversations/{id}`. Single-document conversations are unchanged.
- Retrieval searches all chosen documents in one vector query (an `IN` filter on `document_id`) and takes `max(top_k, 2 x documents)` passages, capped at 12; passages whose text repeats another's (the same file uploaded twice) take one slot.
- A question that asks about every document ("each", "every", "both", "compare", "in common", "differ", "all the documents") skips that search and takes the two best passages of **each** document instead, so a few documents cannot fill every slot. Passages are grouped by document in the prompt, so "summarise each document" gets one entry per document rather than one per passage.
- Each source sent to the model carries its `document` name, and the prompt asks it to say where a fact comes from and to point out when documents disagree.
- Answers have `document_id: null`. Each citation has `document_id`, `filename` and `title` (the document's own title when it has one, otherwise `null`) as well as `page_number` and the quoted `text`, all taken from the stored chunks and documents rather than from the model. The sources the model sees are labelled with the title, or the file name when there is none. `GET /conversations/{id}` fills in each source's current `filename` and `title` from the document, so a rename shows in older answers and answers saved before `title` existed get one. Every validation rule for citations (inline `[n]` labels, one retry) is unchanged.
- Deleting a document removes it from the scope of any multi-document conversation; the conversation and its saved turns remain. Migration `d5a9c3e07b46` makes `conversations.document_id` nullable and adds the `conversation_documents` table.

## Comparative analysis

`POST /comparisons` compares two to five documents and returns a structured result. Uses the `ai` rate limit.

Request: `{"document_ids": [...], "focus": "payment terms"}`. `focus` is optional (up to 200 characters). Every document must be searchable (409 otherwise; 404 for an unknown id). Because each version is its own document, two versions of the same file can be compared the same way.

The model sees, for each document, its saved summary and insights plus the four passages closest to the focus (or to a general "purpose, requirements, terms" query), retrieved **per document** so a long document cannot crowd out a short one. This keeps the request small whatever the document sizes.

Response: `documents` (id, filename, version), `focus`, `overview`, `similarities` and `differences`. Each difference has a `topic` and one `position` per document (`document_id`, `filename`, `statement`; "Not addressed" when a document is silent). The model refers to documents by number; the server maps the numbers back to ids and filenames and rejects drafts with unknown or repeated numbers, fewer than two positions, empty text or more than eight points. `cached: true` means the result came from Redis: results are kept for 7 days under a hash of the model, the sorted document ids and the focus, so listing the same documents in a different order is still a hit.

## Real-time updates (WebSocket)

`WS /ws/events` pushes document changes to the browser as they happen, so the list and the open document update without refreshing.

Messages are JSON text frames:

| Message | Meaning |
| --- | --- |
| `{"type": "ready"}` | Sent once the subscription is active. |
| `{"type": "document.status", "document_id": "...", "status": "processing"}` | A document moved to `queued`, `processing`, `extracted`, `embedded` or `failed`. |
| `{"type": "document.content", "document_id": "..."}` | The automatic summary, insights, category and title finished (or were skipped), so they can be fetched. |
| `{"type": "document.deleted", "document_id": "..."}` | A document (one version) was deleted, so lists should be refetched. |
| `{"type": "document.updated", "document_id": "..."}` | A person changed a document's details (for example renamed it). |

How it works: the worker is a separate process from the API, so it cannot talk to browsers directly. Whenever it (or an upload or reprocess request) changes a status, it publishes the event on the Redis channel `vault:events`. Each WebSocket connection subscribes to that channel in the API process and forwards what it receives. Publishing is best effort and never fails the work it reports.

Events are not stored or replayed. The frontend therefore treats an event as a hint to refetch, not as the new state, and refetches everything after a reconnect (retrying after 1 s, doubling up to 15 s). If Redis is down the socket closes with code 1013 and the UI keeps working with manual refresh. Connect to `/api/ws/events` through the Vite dev proxy (`ws: true`) or directly at `ws://127.0.0.1:8000/ws/events`.

Uvicorn needs the `websockets` package for WebSocket support; it is pinned in `requirements.txt`.
